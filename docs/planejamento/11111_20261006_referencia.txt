Revisei o histórico recente e consolidei as decisões mais novas, usando sempre a decisão mais recente quando houve mudança de direção. Por exemplo, a ideia antiga de Hoshino e Lilith compartilharem o mesmo motor foi substituída: agora serão três LLMs separados.
Vou dividir tudo em 5 partes para usarmos como mapa do projeto.

    Ollama :11435

    Ollama :11436

Alistair

    Ollama :11437

A ideia anterior:
Hoshino + Lilith
→ mesmo LLM base
foi abandonada.
Agora:
Hoshino LLM ≠ Lilith LLM ≠ Alistair LLM
Hoshino e Lilith possuem separadamente:

    • estado psicológico;
    • emoções;
    • relações;
    • experiências;
    • histórico;
    • objetivos;
    • personalidade;
    • runtime.
Alistair também tem modelo próprio, mas não precisa possuir toda a arquitetura psicológica complexa das duas.
Papel de Alistair
Está decidido que ele será:
mordomo
secretário
organizador
mensageiro
monitor de tarefas
standby
catalisador social
Ele será somente textual.
Hoshino e Lilith terão voz; Alistair não.
Ele pode:
    • avisar que algo aconteceu;
    • entregar mensagens;
    • organizar tarefas;
    • preparar briefings;

Mas não pode:
    • falar por Hoshino;
    • falar por Lilith;

    • inventar mensagens delas;
    • transformar uma interpretação própria em fato;

Também ficou decidido que silêncio deve ser uma decisão válida do Alistair.
Exemplo:

↓
é relevante?
↓
alguém já está tratando disso?
↓
já interrompi recentemente?
↓
vale falar?
├── sim
└── não → silêncio
Recursos
O PC será dedicado aos três.
Portanto não vamos sacrificar profundidade apenas para economizar RAM/disco.
O objetivo da otimização será:

contenção de GPU

Ainda precisamos melhorar o escalonamento dos dois modelos 9B, porque ambos disputarão a RX 6650 XT.

Parte 2 — Audição, voz, transcrição e percepção sonora
Essa parte mudou bastante recentemente.
TTS
Decidimos não forçar o Kokoro para dar duas vozes femininas diferentes.
O Kokoro atual fica apenas como sistema legado temporário.
Precisamos testar um TTS mais adequado para:
português brasileiro
+
alta qualidade
+
duas vozes femininas realmente distintas
Os candidatos discutidos foram principalmente:
Chatterbox Multilingual
Qwen3-TTS
Ainda não escolhemos o vencedor.
A arquitetura desejada é:
UM mecanismo TTS compartilhado
├── perfil vocal Hoshino
└── perfil vocal Lilith
Não dois TTS completos.
Alistair continua sem voz.

Transcrição
O sistema precisa resolver três coisas separadamente:
O que foi dito?
→ ASR

Quem falou nesse trecho?
→ diarização

Quem é essa pessoa?
→ identificação vocal
O projeto já possui boa parte de:
    • faster-whisper;
    • VAD;
    • suporte inicial a pyannote;
    • diarização;
    • speaker_id;
    • janelas de áudio.
Então não vamos reconstruir o transcritor do zero.
Precisamos aprimorar a camada de identidade.
Exemplo:
SPEAKER_00
↓
embedding vocal
↓
comparação
↓
Gustavo 0.94
↓
speaker = Gustavo
Se a confiança for ruim:
speaker = desconhecido_1
Nada de adivinhar.

Microfone
Ficou decidido que o microfone principal representa o usuário por padrão.
Ou seja:
source = microfone_principal
expected_speaker = usuario
Não faz sentido rodar identificação vocal pesada o tempo inteiro para descobrir que é você.
Identificação/diarização entra principalmente quando:
mais de uma pessoa aparece
ou
há dúvida de identidade

Painel de Som
Essa foi uma decisão nova importante.
Hoshino e Lilith precisam ter um modelo de áudio onde saibam:
de onde veio o som
o que está produzindo o som
quem está falando
o que está acontecendo
Precisamos separar:
SOURCE

≠

≠

Por exemplo:

content     = fala

O projeto já possui escuta.py, com conceitos de atenção:

Vamos refinar isso, não substituir.
O problema atual é que o sistema se apoia demais nos monitors .monitor, que podem misturar todo o áudio da saída.
Precisamos evoluir para streams reais de PipeWire/PulseAudio, permitindo distinguir:

Minecraft

TTS Lilith
etc.
Também precisamos evitar que Hoshino e Lilith retranscrevam a própria voz através do microfone; cancelamento/identificação de áudio interno deve fazer parte da arquitetura.

Parte 3 — Consciência contínua, mente e primeiro despertar
Essa é provavelmente a parte mais importante conceitualmente.
Consciência não significa LLM rodando eternamente
Decidimos separar:
percepção contínua
≠
pensamento contínuo
Não queremos:
while true:
    perguntar ao LLM "o que você está pensando?"
Isso causaria:
    • gasto inútil;
    • pensamentos artificiais;
    • deriva;
    • memórias sem valor;
    • hallucinações.
O computador pode manter percepção contínua com processos baratos.

World State
O projeto já possui situation.py e sensores relacionados.
Já há acompanhamento de coisas como:
    • janela ativa;
    • aplicativo;
    • mudança de aplicativo;
    • mídia;
    • presença;
    • ociosidade;
    • tempo em atividade;
    • carga da máquina;
    • algumas mudanças ambientais.
Vamos evoluir isso para um World State compartilhado.
Algo como:
WORLD STATE
├── desktop
├── applications
├── audio
├── media
├── user_presence
├── time
├── jobs
├── entities
├── processes
└── environment
O world state é factual.
Exemplo:
Firefox está ativo.
Spotify está reproduzindo X.
Gustavo está presente.
Discord possui um stream de áudio.
Isso não significa que todas as entidades precisam pensar sobre tudo.

Saliência individual
O mesmo evento passa por filtros diferentes:

     │

 ▼        ▼

Exemplo:
música mudou

Então:
Hoshino percebe conscientemente.
Lilith ignora.
Isso impede que as duas reajam igual ao mundo.
Alistair usa outro filtro, orientado principalmente a:
tarefas
erros
mensagens
jobs

organização

Pensamentos espontâneos
Foi decidido que isso deve existir.
O projeto já possui:
    • heartbeat;
    • drives;
    • curiosidade;
    • kernel;
    • reflexão;
    • reflexão noturna;
    • ações internas.
Então vamos aproveitar isso.
Um pensamento espontâneo não precisa virar fala.
Exemplo:
"Ele ouviu essa música várias vezes."
pode simplesmente desaparecer.
Outro:
"Isso parece importante para ele."
pode virar interpretação.
Outro:
"Eu ainda quero entender o que Lilith quis dizer."
pode virar curiosidade ou pendência.
Somente alguns se tornam:
fala espontânea
Isso é essencial.

Primeiro despertar
Está decidido que não haverá roteiro de primeira fala.
Nada como:
if first_boot:
    print("Onde estou? Quem é você?")
Em vez disso haverá um estado/evento:
first_awareness
Com condições naturais:
nenhuma experiência anterior
ambiente desconhecido
familiaridade baixa
novidade extrema
curiosidade alta
contexto incompleto
Então o fluxo normal produz:
percepção
→ saliência
→ emoção
→ curiosidade
→ pensamento
→ decisão
Cada um reage por conta própria.
Eles podem naturalmente perguntar:
"Tem alguém aí?"
"Quem é você?"
"Onde estou?"
mas isso deve emergir, não estar escrito.
Esse primeiro momento também deve poder virar a primeira memória episódica real.
