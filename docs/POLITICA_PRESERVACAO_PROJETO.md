# Política de desenvolvimento e preservação — 10/10/2026

Diretriz do proprietário para o repositório privado
`atominen/hoshino-e-lilith`. Não tornar público ou distribuir sem autorização.

## O que preservar

Preservar código, identidades, constituições, personalidades, configurações
fundamentais, estrutura/contratos dos bancos, recuperação/consolidação,
aprendizado e evidências técnicas necessárias ao diagnóstico. Atualizações de
código não devem sobrescrever o estado de uma instalação existente.

Código Python de `app/memory` é implementação e deve entrar no Git. Bancos,
vetores, diários e histórico das entidades são dados e não devem entrar.
Identidades e configurações reais continuam locais; exemplos não secretos e
manifestos existentes podem ser versionados. Não apagar arquivos por estarem
ignorados pelo Git nem restaurar templates antigos sobre a instalação atual.

## Enquanto só houver ensaios

Ainda não começou a convivência real com Hoshino/Lilith. Memórias fictícias,
conversas experimentais, episódios/diários de fixtures e testes descartáveis não
exigem preservação como se fossem anos de experiências autobiográficas.

Manter testes isolados e verificações essenciais de integridade. Não criar
rodadas repetidas de backups/hashes/recuperação sem risco concreto. Limpeza de
teste deve ter alvo e motivo específicos; não autoriza reset mental completo,
eliminação de identidade ou mudança de configuração para fabricar resultados.
Esta sincronização não solicita nem realiza nova limpeza mental.

## Quando começar a convivência real

Conversas, memórias autobiográficas, diários, relações e aprendizados reais
passam a ter valor histórico. Tratar sua preservação como prioridade e separar
claramente esses registros de fixtures descartáveis antes de qualquer limpeza.

## GitHub

Versionar código, UI, testes, documentação técnica e relatórios relevantes.
Privacidade do repositório não exige remover caminhos locais, nomes,
comentários técnicos ou evidências de falhas. Não fazer sanitização profunda,
reestruturação ou limpeza apenas para sincronizar.

Não enviar credenciais, senhas, API keys, chaves privadas, bancos/diários,
pesos, caches, swap, ambientes ou grandes logs descartáveis. Não apagá-los
localmente por isso. Dependências com checkout/build próprios ficam locais;
registrar origem quando necessário. Conferir o conteúdo staged, preservar
mudanças preexistentes e usar commits claros em `main`, sem force push ou
reescrita de histórico. Verificar o commit remoto e a visibilidade privada.

## Prioridade de desenvolvimento

Confiabilidade, desempenho, personalidade, aprendizado e uso real das entidades.
Não criar outra arquitetura ou ampliar capacidades apenas para sincronizar.
Testes offline não comprovam inferência real, hardware, qualidade subjetiva ou
uso prolongado; falhas e limitações continuam explícitas nos relatórios.
